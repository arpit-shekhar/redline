# Spec: Redline v1 — trustworthy document analysis

Status: ready-for-agent

Source: `PRD.md`. Vocabulary: `CONTEXT.md`. Binding decisions: `docs/adr/0001`
through `0005`. Where this spec and an ADR disagree, the ADR wins.

**Confirm before starting: the seams in "Implementation Decisions → Seams".**
Everything else follows from the PRD; the seams are the one thing chosen here
rather than inherited, and they determine what can be tested.

---

## Problem Statement

A freelancer or small business owner is holding a document they have not yet
signed — a contract, a lease, a freelance agreement, or a set of terms of
service. They cannot tell which parts of it will hurt them.

Today they sign it unread (62% of small business owners admit signing a contract
they did not fully understand), or they pay $250–$750 for a lawyer to read it,
or they find that price out of reach. When something goes wrong, they discover
it at the exit: cancelling, leaving, chasing an invoice. By then there is
nothing to negotiate.

The obstacle is not that plain-English contract summaries do not exist. They do,
including free ones. The obstacle is that a summary written by a machine is
unverifiable — the reader cannot tell an accurate reading from a confident
invention, so they cannot safely act on either. A tool that is right most of the
time, with no way to tell which time this is, does not support a decision.

## Solution

Redline reads the document in the browser, extracts its text, and returns an
analysis where every claim can be checked against the document itself.

Each **flag** — a clause that could hurt this user — is shown beside the
**source sentence** it came from, quoted word for word from the document. The
user can search their own copy for that sentence and judge whether Redline read
it correctly. Flags carry one of two severities, ranked by **escapability**: how
hard it is to get out of the obligation once signed.

For every flag, Redline drafts a **counter-offer** — replacement wording the
user can send — toned according to the **leverage** they told us they have.

A **question box** answers only from the document, and declines when the
document does not say.

When a document is clean, Redline says so and shows what it checked for, rather
than returning silence the user cannot distinguish from a broken analysis.

## User Stories

**Getting a document in**

1. As a freelancer, I want to upload a PDF of an unsigned contract, so that I can find out what it does to me before I sign it.
2. As a small business owner, I want to upload a Word document, so that I am not forced to convert files before getting an answer.
3. As a user, I want to paste text directly instead of uploading a file, so that I can analyse a contract that arrived in the body of an email.
4. As a privacy-conscious user, I want my file to be read in my own browser and never sent anywhere, so that the document itself never leaves my machine.
5. As a user, I want to be told plainly that only the extracted text is stored and the file is discarded, so that I know what I am agreeing to.
6. As a user uploading a scanned document, I want to be told clearly that Redline cannot read scans and why, so that I do not receive a confident analysis of text that was never read correctly.
7. As a user, I want to be told when a document is too long to analyse, so that I am not left waiting on something that will not finish.
8. As a user, I want to tell Redline what kind of document this is, so that the analysis looks for the clauses that actually apply to it.

**Understanding the document**

9. As a user, I want a plain-English summary of the document, so that I understand what I am signing without reading every clause.
10. As a user, I want the summary to describe what the document does rather than restating its structure, so that it saves me the reading rather than duplicating it.

**Seeing what could hurt me**

11. As a user, I want the clauses that could hurt me listed and ranked, so that I know what to deal with first.
12. As a user, I want each flag shown beside the exact sentence it came from, so that I can check Redline against the document rather than trusting it.
13. As a user, I want to find that quoted sentence in my own copy of the document, word for word, so that I can confirm nothing was paraphrased or invented.
14. As a user, I want flags split into must-change and worth-raising, so that I know which ones are worth risking the deal over.
15. As a user, I want to understand why a flag is must-change rather than worth-raising, so that I can disagree with the ranking if my situation differs.
16. As a user, I want statements about what the clause *says* to be stated plainly, so that useful information is not buried in hedging.
17. As a user, I want statements about what a clause *might do to me* marked as uncertain, so that I do not mistake a prediction for a fact.
18. As a user, I want to see the clause in the context around it, so that I can judge whether the flag reads the sentence fairly.
19. As a user with a clean document, I want to be told it is clean and shown what was checked for, so that I can tell a genuinely fair contract from a failed analysis.
20. As a user, I want flags to appear in a stable order between runs, so that a document I re-analyse does not look different for no reason.

**Doing something about it**

21. As a user, I want a drafted counter-offer for every flagged clause, so that I can push back without knowing how to write contract language.
22. As a user who cannot afford to lose this deal, I want counter-offers worded as requests rather than demands, so that asking does not cost me the work.
23. As a user who can walk away, I want counter-offers worded firmly, so that I am not negotiating more weakly than my position allows.
24. As a user, I want to state once whether I can walk away, so that I am not asked the same question for every document.
25. As a user, I want to copy a counter-offer in one action, so that I can paste it into an email to the other side.
26. As a user, I want to edit a counter-offer before sending it, so that it sounds like me rather than like a tool.

**Asking questions**

27. As a user, I want to ask a question about the document in my own words, so that I can check something specific that the flags did not cover.
28. As a user, I want answers drawn only from this document, so that I am not given general legal advice dressed up as a reading of my contract.
29. As a user, I want the answer to quote the part of the document it came from, so that I can verify it the same way I verify a flag.
30. As a user asking something the document does not address, I want to be told the document does not say, so that silence is not filled with a plausible guess.

**Setting my own rules**

31. As a user, I want to see the default list of clauses Redline flags, so that I know what it is looking for before I trust its result.
32. As a user, I want to turn off a clause type I do not care about, so that my analysis is not cluttered with things I have already accepted.
33. As a user, I want to add my own red line in my own words, so that the analysis reflects what actually matters to me.
34. As a user, I want to change a clause type's default severity, so that a clause that is fatal in my line of work is ranked as fatal.
35. As a user, I want my red lines to persist across documents, so that I set them once rather than every time.

**Keeping my documents**

36. As a returning user, I want a library of documents I have analysed, so that I can go back to one without re-uploading it.
37. As a user, I want to see when each document was analysed, so that I know whether the analysis predates a change I made to my red lines.
38. As a user, I want to delete a document and its text permanently, so that I control how long my contract text is retained.
39. As a user, I want my library visible only to me, so that my contract text is not exposed to anyone else.
40. As a user, I want to sign in and find my red lines and library where I left them, so that the product is worth returning to.

**When things go wrong**

41. As a user, I want to be told when the analysis failed rather than shown a partial result, so that I do not act on an incomplete reading.
42. As a user, I want to retry a failed analysis without re-uploading, so that a transient failure does not cost me the work of starting over.
43. As a user, I want to be told if a flag was dropped because its source sentence could not be verified, so that the count I see is honest about what was withheld.

## Implementation Decisions

### Seams

There is no existing code, so every seam is new. Three are proposed; the first
is where the product's trustworthiness is won or lost, and it should carry
nearly all of the testing weight.

**Seam 1 — the analysis core (primary).** One module boundary, two entry points.
This is the highest seam available: everything above it is presentation,
everything below it is the model call.

- **Analyse.** Takes the document text, its type, the user's red lines, and the
  user's leverage. Returns an analysis: a summary, an ordered list of flags, and
  the list of clause types checked for.
- **Answer.** Takes the document text and a question. Returns either an answer
  with the passage it came from, or a refusal.

Both are ordinary functions over data. They own the model call; nothing above
them knows a model exists. Six of the PRD's seven checks are testable here.

**Seam 2 — text extraction.** Takes a file, returns document text plus whatever
position information is needed to locate a sentence again. Runs in the browser.
Separate from seam 1 because the guarantee in ADR 0001 depends on the stored
text being a faithful copy: if extraction mangles the text, every source
sentence downstream fails to match and the failure looks like a model problem.

**Seam 3 — storage.** Persists document text, analyses, red lines, leverage, and
library membership per user. Tested as ordinary data access, not as part of the
trust guarantee.

Authentication, routing, and rendering are tested through the running app rather
than at a seam of their own.

### The analysis contract

A **flag** carries these fields. The shape matters because it makes the PRD's
rules structural rather than a matter of prose style.

| Field | Purpose |
|---|---|
| Clause type | One of the eight defaults, or a user's own red line |
| Severity | Exactly two values: must-change, worth-raising |
| Source sentence | The exact sentence, quoted from the document text |
| Source location | Where that sentence sits, so it can be highlighted |
| Text claim | What the clause says. Stated plainly, no hedging |
| Outcome claim | What it might do to the user. Always marked uncertain |
| Escapability reasoning | Why this severity, in terms of how hard it is to exit |
| Counter-offer | Replacement wording, toned by leverage |

Keeping **text claim** and **outcome claim** as separate fields is the decision
that makes ADR 0004 enforceable. If both lived in one prose blob, "is every
outcome claim marked uncertain?" would be a question about writing style. Split,
it is a question about data, and a test can answer it.

A **clean result** is not an empty flag list. It carries the list of clause types
checked for, so the user can tell a fair document from a failed analysis.

### Source sentence verification is a runtime gate, not only a test

Before any analysis is returned, every flag's source sentence is checked against
the stored document text. A flag whose sentence is not found word for word is
**dropped, counted, and logged** — never shown.

This follows from ADR 0001 making an unshowable source sentence a bug rather
than a limitation. It has two consequences worth stating plainly:

- Users never see an unverifiable citation, because unverifiable flags do not
  reach them.
- The eval suite must therefore measure the drop rate *before* the gate, not the
  citation accuracy after it. Measuring after the gate always returns 100% and
  tells you nothing.

Normalisation for whitespace and typographic quotes is expected. Normalisation
that would let a paraphrase pass is not.

### Model access

The product calls its model through OpenRouter using `anthropic/claude-opus-5`,
pinned in one module so there is a single place to change it. That exact model
name must be confirmed against OpenRouter's live model list on the first call.
The model is not to be changed without asking (`CLAUDE.md`).

### Other decisions

- **Only text is stored, never the file.** Parsing happens in the browser; the
  file never reaches the server.
- **Scanned documents are refused, not attempted.** When extraction yields no
  usable text, the user is told the document appears to be a scan and that
  Redline does not read scans. No OCR, no partial analysis, no guessing.
- **Leverage lives with red lines**, not as a per-document prompt (ADR 0005). It
  is a standing fact about the user.
- **Red lines drive the analysis**, so a user's edits change what is looked for,
  not just what is displayed.
- **Flag ordering is deterministic** — severity first, then document position —
  so that re-analysing a document does not shuffle the result.

## Testing Decisions

### What makes a good test here

Tests exercise a seam's external behaviour: text in, structured analysis out.
They do not reach into prompt construction, retry logic, or response parsing —
those are free to change. A test that breaks when the prompt is reworded, while
the analysis stays correct, is testing the wrong thing.

**There is no prior art. This spec establishes it**, so the first tests written
set the pattern for everything after.

### Two tiers, because two different things are being measured

**Structural tests — fast, deterministic, gate every build.** These run against
recorded analysis outputs and never call the model. They check shape and
invariants:

- Every flag's source sentence appears word for word in the document text it
  came from (PRD check 1).
- Every outcome claim carries an uncertainty marker; no text claim does (check 7).
- Severity is only ever must-change or worth-raising.
- A clean result carries a non-empty checked-for list.
- Flag ordering is stable across repeated runs of the same input.
- Extraction round-trips a known file to known text, so a sentence found in the
  original is findable in the stored text (seam 2).

**Quality evals — slow, cost real money, run deliberately.** These call the live
model against the review set and measure judgement, not shape:

- Must-change precision: a reviewer with relevant expertise agrees with the
  must-change call. Target 90% or better (check 2).
- Planted-trap recall: documents seeded with known clauses of known type, flagged
  at either level. Target 95% or better (check 3).
- Benign documents produce zero must-change flags (check 4). Some worth-raising
  flags are acceptable.
- The question box refuses what the document does not address, with no answer
  drawn from outside it (check 5).
- Counter-offer sendability, human-judged. No target until a baseline exists
  (check 6).
- **Pre-gate citation drop rate**, measured before verification removes bad
  flags — the honest measure of how often the model invents a quote.

### The blocking dependency

**Checks 2, 3, 4, and 6 cannot run until a review set exists**: real documents of
the four supported types, with expert judgements attached, plus a set of
deliberately benign documents and a set with planted clauses. The PRD names
building this as the first engineering task and warns it is not small.

Two constraints on that set, both from decisions already made: the documents are
other people's contracts, so the set must not be committed to this public
repository; and it must contain benign documents, because check 4 is the one
that catches over-flagging and there is nothing to measure without them.

### Watch the tension between check 3 and check 4

The PRD chose to over-flag rather than miss traps (call 7) and also chose to give
clean documents a checklist (call 9). Those pull against each other. The eval
suite should report checks 3 and 4 side by side, because a build that improves
recall by inflating the must-change count has broken the severity model while
appearing to get better.

## Out of Scope

From `CLAUDE.md` and PRD section 7, unchanged:

- **Payments and billing.** No price has been decided; nothing here depends on one.
- **OCR.** Excluded deliberately, and it makes scanned documents unreadable
  rather than degraded. The share of real documents arriving as scans has never
  been measured — that number is worth finding before this is treated as settled.
- **Sharing a document between users.**
- **Helping people who have already signed.** The larger and better-evidenced
  problem, deliberately out of scope.
- **Flagging what is missing from a document** — absent late-payment interest, no
  kill fee, no rights reverting on non-payment. The strongest candidate for the
  next thing built, and excluded now only because it is a seventh capability that
  `CLAUDE.md` requires asking about first.

Also out of scope for v1: exporting an analysis, comparing two documents,
tracking a negotiation across versions, and any clause type outside the eight
defaults plus the user's own red lines.

## Further Notes

**ADR 0002 is still marked `proposed`.** It carries the segment, the four
document types, and the pre-signature timing — three of the most load-bearing
decisions here — and its reasoning is reconstructed rather than stated. Worth
resolving before large amounts of work depend on it.

**The riskiest assumption is not technical.** Four researchers found nobody at
the pre-signature moment. If that moment does not exist, no amount of detection
accuracy saves the product. Nothing in this spec tests that; it is a product
question and it outranks everything here.

**The counter-offer is the only capability separating Redline from free
alternatives** already in this segment, and no evidence exists that anyone
actually sends one. That makes counter-offer quality (check 6) more strategically
important than its "no target yet" status suggests.

**Eight clause types across four document types is 32 combinations**, each
needing detection, severity calibration, and a counter-offer, each bound by
ADR 0001. If schedule pressure appears, this is the first place to look for
scope to cut — and the exit-trap family (automatic renewal, cancellation terms,
notice periods, early-termination fees) is the part with verified evidence
behind it.
